--------------------------------------------------------------
2.1 ASVS 2.1.1 — Contraseñas de al menos 12 caracteres  [NUEVO]
--------------------------------------------------------------
  Qué exige: las contraseñas deben tener al menos 12 caracteres de longitud.

  Qué cambié: la regla de validación en los tres puntos donde se define o
  cambia una contraseña subió a 'min:12'.

  Código afectado (líneas actuales):
    - app/Http/Controllers/Auth/RegisterController.php      :28
        'password' => ['required', 'string', 'min:12', 'confirmed'],
    - app/Http/Controllers/UserController.php               :29  (crear usuario)
        'password' => 'required|string|min:12|confirmed',
    - app/Http/Controllers/UserController.php               :67  (editar usuario)
        'password' => 'nullable|string|min:12|confirmed',

  Cómo funciona: Laravel ejecuta estas reglas de validación durante el
  'validate()' del controlador ANTES de tocar la base de datos. Si la
  contraseña es menor a 12 caracteres, el request se rechaza con el error de
  validación estándar y NO llega a generarse el hash.

  Qué afecta: ningún usuario puede usar contraseñas débiles (< 12). También
  aplica al cambio de contraseña de un usuario existente (campo opcional; si
  viene vacío no se valida — se conserva la contraseña actual).

--------------------------------------------------------------
2.2 ASVS 2.4.1 / 2.4.2 / 2.4.4 — Almacenamiento seguro de contraseñas
--------------------------------------------------------------
  Qué exige: hash con sal, de una sola vía, con factor de costo (bcrypt),
  sal >= 32 bits única por credencial, work factor bcrypt >= 10.

  Código afectado (líneas actuales):
    - app/Models/User.php:32
        'password' => 'hashed',   // cast: hashea en el setter del modelo
    - app/Models/User.php:17
        #[Hidden(['password', 'remember_token'])]  // nunca se serializa
    - app/Http/Controllers/Auth/RegisterController.php:34
        'password' => Hash::make($request->password),
    - app/Http/Controllers/UserController.php:35  y :74
        'password' => Hash::make(...),
    - app/Http/Controllers/Auth/LoginController.php:25
        Auth::attempt($credentials, ...)  // verificación (nunca almacena)
    - database/migrations/0001_01_01_000000_create_users_table.php:19
        $table->string('password');  // columna varchar(255) en BD

  Cómo funciona el flujo completo:
      "admin12345" (texto plano, nunca se persiste)
         |
         | Hash::make()           (RegisterController:34 / UserController:35,74)
         v
      "$2y$12$bE9..." (bcrypt; sal 126 bits; 2^12 iteraciones)
         |
         | cast 'hashed' detecta que YA es hash -> lo guarda tal cual (User.php:32)
         v
      BD users.password   (oculto en respuestas por User.php:17)
         |
         | Auth::attempt()  -> Hash::check(entrada, hash)   (LoginController:25)
         v
      true / false

  Qué afecta: si la base de datos se filtra, un atacante no puede recuperar
  contraseñas en claro ni aplicar diccionarios/rainbow tables de forma
  efectiva (cada hash tiene sal única y cuesta ~2^12 operaciones). Cumple:
    - 2.4.1  hash con sal, una vía, costo          -> CUMPLE
    - 2.4.2  sal >= 32 bits única por credencial  -> CUMPLE (≈126 bits)
    - 2.4.4  work factor bcrypt >= 10             -> CUMPLE (coste 12)

--------------------------------------------------------------
2.3 ASVS 2.4.3/2.4.4 — Rehash bajo demanda  [NUEVO]
--------------------------------------------------------------
  Qué exige: si el coste del algoritmo aumenta en el futuro, las contraseñas
  existentes deben migrarse al nuevo coste sin pedir al usuario que cambie su
  contraseña.

  Qué cambié: en el login correcto, si el hash almacenado usa un coste menor al
  configurado, se re-hashea con el nuevo y se guarda.

  Código afectado (líneas actuales):
    - app/Http/Controllers/Auth/LoginController.php:27-31
        if (Hash::needsRehash(auth()->user()->password)) {
            auth()->user()->update(['password' => Hash::make($request->password)]);
        }

  Cómo funciona: Laravel compara el "cost" contenido dentro del propio hash
  (el '$12' de "$2y$12$...") contra el coste de config('hashing.bcrypt.rounds').
  Si el coste actual es menor, se regenera el hash con la contraseña recién
  verificada (nunca con texto plano nuevo) y se persiste. Si el coste ya es el
  configurado, no se hace nada (cero sobrecarga).

  Qué afecta: futuras subidas del coste en config/hashing.php migran toda la
  base de usuarios automáticamente en su siguiente login, sin afectar al
  rendimiento del resto del tiempo. Sin este bloque, subir el coste dejaría
  antiguas contraseñas con cifrado más débil indefinidamente.

--------------------------------------------------------------
2.4 ASVS 2.2.1 — Anti-automatización / fuerza bruta
--------------------------------------------------------------
  Qué exige: controles anti-automatización que mitiguen pruebas de
  credenciales, fuerza bruta y bloqueo de cuentas.

  Código afectado (líneas actuales):
    - app/Providers/AppServiceProvider.php:30-38
        RateLimiter::for('login', function (Request $request) {
            return Limit::perMinute(5)
                ->by($request->input('email') . '|' . ($request->ip() ?? 'anon'));
        });
        RateLimiter::for('register', function (Request $request) {
            return Limit::perHour(5)
                ->by($request->ip() ?? 'anon');
        });
    - routes/web.php:36  -> Route::post('/login', ...)->middleware('throttle:login');
    - routes/web.php:38  -> Route::post('/register', ...)->middleware('throttle:register');

  Cómo funciona: el middleware 'throttle:login' consulta el RateLimiter
  'login'. La clave es email+IP del cliente; se permiten 5 intentos por
  minuto. Al superarlo, Laravel responde HTTP 429 "Too Many Requests".

  Verificación real: intentos 1-5 -> 302 (credenciales incorrectas);
  intentos 6 y 7 -> 429 (bloqueado).

  Qué afecta: un atacante no puede probar contraseñas masivamente; al sexto
  intento por dirección IP+usuario queda limitado. Nota ASVS 2.2.1: el tope
  literal del estándar es "menos de 100 intentos fallidos por hora por cuenta"
  (5/min = ~300/h); si se requiere cumplimiento estricto, bajar a
  perMinute(1).

2.5 ASVS 2.3.1 — Control del ciclo de vida del registrador (registro cerrado)
--------------------------------------------------------------
  Qué exige: las cuentas no deben poder crearse automáticamente con
  privilegios elevados sin evidencia de identidad.

  Código afectado (líneas actuales):
    - app/Http/Controllers/Auth/RegisterController.php:52-57
        private function ensureRegistrationOpen(): void
        {
            if (User::count() > 0) {
                abort(403, 'El registro público está deshabilitado.');
            }
        }
    - Registro GET -> RegisterController.php:16  (llamada a ensureRegistrationOpen)
    - Registro POST -> RegisterController.php:23 (idem)
    - Rol del primer usuario -> RegisterController.php:39-40 ('Administrador')
    - app/Http/Controllers/Auth/LoginController.php:14
        'registrationOpen' => \App\Models\User::count() === 0,
    - resources/views/auth/login.blade.php:61  -> oculta el enlace "Regístrate"

  Cómo funciona: si ya existe al menos un usuario, GET o POST /register
  devuelven HTTP 403. El único momento en que el registro funciona es el
  "bootstrap" inicial (base de datos vacía), y ese primer usuario es el que
  obtiene el rol Administrador. El formulario de login sólo ofrece enlace de
  registro mientras no haya usuarios.

  Qué afecta: elimina la escalada de privilegios por "registro abierto" (el
  antiguo comportamiento otorgaba rol Admin en RegisterController), y limita
  la creación de cuentas al panel de administración.

3.1 ASVS 4.1.1 / 4.1.3 — Reglas en capa de confianza y privilegios mínimos
--------------------------------------------------------------
  Qué exige: las decisiones de autorización deben aplicarse en el servidor
  (no en el cliente) y los usuarios sólo deben poder acceder a lo que su rol
  les autoriza.

  Código afectado (líneas actuales):
    - routes/web.php:56   Route::middleware('role:Administrador')->group(  // users, roles
    - routes/web.php:68   Route::middleware('role:Administrador,Secretario')->group( // cargos, lideres, miembros,
                                ministerios, actividades, seguimiento, cursos, inscripciones, pagos, docentes, sesiones, asistencia)
    - routes/web.php:130  Route::middleware('role:Administrador,Tesorero')->group( // cultos, ingresos, egresos, contratos
    - resources/views/layouts/app.blade.php:31    -> categoria "Acceso y Seguridad" solo Administrador
    - resources/views/layouts/app.blade.php:61    -> item "Cultos" solo Admin|Tesorero
    - resources/views/layouts/app.blade.php:87    -> item "Contratos" solo Admin|Tesorero
    - resources/views/layouts/app.blade.php:111   -> items "Ingresos/Egresos" solo Admin|Tesorero

  Cómo funciona: el middleware 'role' (app/Http/Middleware/RoleMiddleware.php,
  alias registrado en bootstrap/app.php) se ejecuta en el servidor para cada
  request. Comprueba el rol del usuario autenticado contra la lista definida
  en la ruta; si no coincide -> HTTP 403. El menú (app.blade.php) además
  oculta las opciones no permitidas.

  Verificación real:
    - admin@proyecto.com  -> /users 200, /cultos 200, /cargos 200
    - secretario         -> /cargos 200, pero /cultos 403, /ingresos 403, /users 403
    - tesorero           -> /cultos 200, pero /miembros 403, /cargos 403

  Qué afecta: incluso si un usuario adivina la URL de un módulo prohibido,
  recibe 403. No basta ocultar el menú: la regla se aplica en la ruta.
